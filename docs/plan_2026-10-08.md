# 실시간 음성 입력 엔진 — 기획 검토 및 1단계 개정 기획안

[2026-10-08] · @JD

## 총평

방향은 맞다. 다만 지금 구조로는 최대 성능이 나오지 않는다. 정확도를 가장 크게 올리는 지점이 STT 뒤의 보정이 아니라 STT 안쪽(용어 바이어싱)인데, 원 기획은 보정을 전부 STT 뒤에 직렬로 쌓아두었다.

유지할 것은 세 가지다. 공통 Core를 UI와 분리한 설계, Push-to-Talk → Always Listening의 확장 순서, Fast/Final 보정 분리. 이 셋은 그대로 간다.

바꿀 것은 다섯 가지다.

1. **보정의 1차 책임 주체를 STT 엔진으로 옮긴다.** 용어 사전은 먼저 STT 엔진에 키워드 부스팅/프롬프트로 주입하고, 사후 보정(사전·음소·문맥)은 2차 방어선으로 둔다. "마뤼아뒤비"가 애초에 덜 나오게 하는 쪽이 사후에 고치는 쪽보다 빠르고 정확하다.
2. **Partial은 화면에만, 커서 입력은 확정 단위로만.** 실시간으로 바뀌는 Partial을 OS 커서에 직접 쓰면 지우고 다시 쓰는 문제로 다른 앱의 입력이 깨진다.
3. **음소 보정에 "영문 용어 → 한글 발음 표기" 생성을 추가한다.** 한국어 STT는 영문 용어를 한글로 적는다. 자모 거리만으로는 "MariaDB"와 비교할 대상이 없다.
4. **VocabularyManager는 파이프라인 단계가 아니라 보정기들이 공유하는 자원이다.** 직렬 다이어그램에서 빼고 옆에 둔다.
5. **평가 체계를 Phase 1-1부터 만든다.** 개인 발화 테스트셋, 용어 정확도, 오보정률, 지연 p50/p95 없이는 "보정이 좋아졌는지"를 판단할 수 없다.

**2026-10-08 개정**(Claude·codex 교차검증 반영)에서 더 바꾼 것: 모델 후보표를 2026년 10월 기준으로 교체(1차 Nemotron 3.5 스트리밍, 2차 Qwen3-ASR), STT는 sherpa-onnx 단일 런타임을 기본으로, Verbatim 경로에서 LLM 제외, 게이트 정의(1-0·1-2·1-3·1-4) 수정, 지연 예산 표에 2차 재인식 행 분리, 발화 버퍼와 링버퍼 구분, 홀드아웃 세트 분리. 원 기획 항목별 판정과 2단계 세부 메모는 부록 탭으로 옮겼다.

## 용어 정리

이 문서에서 쓰는 용어와 각각을 담당하는 주체다.

| 용어 | 뜻 | 담당 주체 |
|---|---|---|---|
| Voice Core | 마이크 소리를 받아 최종 텍스트로 만드는 공통 엔진. 버튼·화면 코드와 분리된 내부 처리 덩어리 | 엔진 코드 (UI와 별개) |
| Controller | 언제 듣기 시작하고 끝낼지만 정하는 부분. 1단계는 단축키, 2단계는 VAD | 앱 쪽 코드 |
| STT | 음성을 텍스트로 바꾸는 인식 모델 | 로컬 STT 모델 |
| 바이어싱 | STT 모델에 "이 단어들이 나올 수 있다"고 미리 알려 인식을 그쪽으로 기울이는 기능 | STT 모델 |
| Partial / Final | 말하는 도중의 임시 결과 / STT가 확정한 결과 | STT 모델 |
| 용어 사전 | 정식 표기(MariaDB)와 그 한글 발음들(마리아디비 등)을 묶은 목록 | VocabularyManager |
| Fast Correction | 말하는 도중 수 ms 안에 하는 가벼운 보정. 사전·발음 비교만 쓴다 | 규칙 기반 코드 |
| Final Corrector | 말을 끝낸 뒤 문장 전체를 한 번 더 다듬는 단계 | 로컬 LLM |
| Verbatim 모드 | 말한 그대로 두고 오인식·용어·문장부호만 고친다 | Final Corrector |
| Polished 모드 | "음", "그" 같은 군말을 빼고, 말을 바꾼 부분을 반영해 깔끔한 문장으로 만든다 | Final Corrector |

## 원 기획 검토

원 기획 항목별 판정(유지 / 보완 / 변경)과 빠진 네 가지는 @file/e933317f-2774 탭에 있다. 결론만 적으면, 유지할 것은 Core 분리·PTT→상시 청취 순서·Fast/Final 분리이고, 빠진 것은 STT 엔진 선정 기준·용어 바이어싱·평가 체계·OS 입력 주입 방식이다.

## 1단계 개정 아키텍처

구조는 세 계층으로 나누고, 각 계층의 책임 주체를 한 가지 질문으로 고정한다.

- **Controller (언제 들을까):** 녹음 시작·종료만 결정한다. 1단계는 PushToTalkController, 2단계에 AlwaysListeningController가 같은 자리에 붙는다.
- **Voice Core (무엇을 들었나):** 오디오 → STT → 버퍼 → 보정까지. 결과를 반환하지 않고 이벤트로 발행한다.
- **Adapter (어디로 보낼까):** 오버레이 표시, 커서 입력. 대상이 늘어나도 Core는 바뀌지 않는다.

[아키텍처 다이어그램 — "용어 사전은 STT와 보정 양쪽에 들어가고, 커서에는 확정본만 간다" (2026-10-08 라벨 갱신)]

- 상단: PushToTalkController(단축키 ON·OFF) → Voice Core. AlwaysListeningController(VAD, 2단계, 점선). 오버레이 UI(Partial 실시간 표시) ← Partial 이벤트.
- Voice Core: AudioCapture(20ms PCM · 발화 버퍼 · 30초 링버퍼) → STT Adapter(sherpa-onnx · hotword/context 주입) → TranscriptBuffer(확정·안정·변동) → 발화 종료 → Fast Correction(후보 생성 → Ranker) → Final Corrector(로컬 LLM · Polished만 · 상한 800ms) → OutputAdapter(클립보드 붙여넣기) → 확정본 → 대상 앱 커서.
- VocabularyManager(용어·발음 표기·사용 빈도) → STT Adapter(바이어싱), → Fast Correction. 수정 로그(오디오·원문·최종) → 개인화 → VocabularyManager.

원 기획과 달라진 점은 세 가지다. VocabularyManager(강조)가 직렬 단계에서 빠져 STT 엔진과 Fast 보정이 함께 참조하는 자원이 됐다(Final Corrector도 같은 용어 목록을 프롬프트로 받는다). Partial은 오버레이로만 가고, 대상 앱 커서에는 Final 보정을 거친 확정본만 들어간다. 수정 로그가 1단계부터 사전으로 다시 흘러 들어간다.

## 처리 흐름과 실행 구조

"MariaDB 커넥션 풀 확인해줘"를 말했을 때 엔진 안에서 일어나는 일 전체다. AI 모델은 세 군데(5·10·12번)뿐이고, 나머지는 전부 엔진 코드가 처리한다.

### 동시 처리 구조

말하는 동안(1~9번)은 네 갈래가 동시에 돈다. 서로 기다리지 않기 때문에 말하는 도중에 글자가 따라 나온다.

| 갈래 | 담당 | 하는 일 | 움직이는 시점 |
|---|---|---|---|---|
| A | 단축키 감지 (1·9번) | 단축키를 뗐는지 감시 | 항상 대기 |
| B | 소리 수집 (3·4번) | 20ms 조각 수집·정리 | 20ms마다 |
| C | 1차 STT (5번) | 쌓인 조각을 인식 | 조각이 모일 때마다 (GPU) |
| D | 결과 처리 (6→7→8번) | 관리 → 보정 → 표시 | C가 결과를 낼 때마다 (수 ms) |

단축키를 뗀 뒤(10~16번)는 앞 단계 결과가 있어야 다음 단계를 할 수 있으므로 순서대로 한 번 실행한다. 이 구간 전체가 "발화 종료 → 커서 입력 p50 700ms" 목표에 들어가야 한다.

### 모델 실행 방식

STT 모델과 LLM 모두 **엔진 프로세스 안에 내장**한다. 외부 서버 프로그램(LM Studio 등)은 쓰지 않는다.

- STT는 **sherpa-onnx 단일 런타임**을 기본으로 한다. 1차 Nemotron 스트리밍과 2차 Qwen3-ASR 오프라인이 같은 런타임·같은 hotword 형식으로 돌고, Windows 네이티브·프로세스 내장·CPU↔CUDA 전환이 provider 설정 하나다.
- transformers·vLLM·OpenVINO 백엔드는 1-0 비교용 별도 가상환경에서만 쓴다. qwen-asr 0.0.6은 transformers==4.57.6을 고정하고 Cohere는 transformers>=5.4를 요구해 한 환경에 못 넣는다.
- 엔진이 시작할 때 사용할 모델을 모두 적재해 상주시킨다. 외부 서버 프로그램은 쓰지 않는다(사용자 결정).
- LLM은 Polished 경로에서만 llama.cpp(GGUF)로 같은 프로세스에 적재하고, 고정 지시문은 미리 계산해 재사용한다.
- 모델 교체는 설정 파일에서 어댑터 종류·모델 이름·provider를 함께 바꾼다. 샘플레이트·청크·hotword 형식이 어댑터마다 다르므로 경로만 바꿔서는 안 된다.

## STT 엔진 전략

STT 엔진은 하나를 정하고 시작하지 말고, 어댑터 뒤에 2~3개를 꽂아 개인 테스트셋으로 비교한 뒤 고른다. 선정 기준은 최종 출력(커서 입력본)의 용어 재현율·CER·오삽입·지연이며, 그다음이 "용어 바이어싱 지원 여부"다.

### 용어 바이어싱이 1차 방어선인 이유

STT 엔진(주체: 음성 인식 모델)은 디코딩 중에 후보 단어를 고른다. 이때 "MariaDB", "Spring Boot" 같은 용어 목록을 넣어주면 엔진이 그 쪽으로 기운다. 사후 보정(주체: CorrectionEngine)은 이미 잘못 적힌 글자만 보고 추측해야 한다. 오디오 정보를 가진 쪽이 고치는 게 원리적으로 더 정확하다.

따라서 VocabularyManager의 용어 목록은 두 곳으로 동시에 흘러간다. 하나는 STT 엔진의 부스팅 설정, 다른 하나는 CorrectionEngine의 후보 사전이다.

| 1차 STT (Nemotron int8) | CPU 실행 시 0 / CUDA 시 1GB 미만 |
| 2차 STT (Qwen3-ASR-1.7B) | ONNX int8 약 2GB (추정) / bf16 약 3.5GB |
| LLM (Gemma 4 E4B 또는 Qwen3.5-4B, Q4 GGUF, 문맥 캐시 포함) | 약 5~6GB (추정) |
| Windows 화면 등 | 약 1GB |
| **합계** | **추정 10~13GB. 동시 적재 peak는 1-0에서 실측** |

후보는 비교할 때만 하나씩 올리고, 최종 선택된 것만 상주시킨다. 합계는 파일 크기에서 유도한 추정이며 캐시·활성값은 빠져 있으므로 동시 적재 후 긴 발화의 peak를 실측한다. LLM은 4bit 양자화(GGUF)를 쓴다.

## Correction Engine 재설계

CorrectionEngine은 "4단 직렬 필터"에서 "후보 생성 → 점수 합산 → 임계값 판정" 구조로 바꾼다. 각 보정기는 결과를 덮어쓰지 않고 후보와 점수만 낸다. 최종 결정은 Ranker 한 곳에서 내린다.

### 주체별 역할

| 주체 | 하는 일 | 하지 않는 일 | 지연 목표 |
|---|---|---|---|---|
| VocabularyManager | 정식 용어(Canonical), 등록된 발음 변형, 자동 생성된 한글 발음 표기, 사용 빈도를 보관 | 보정 판단 | 조회 1ms 미만 |
| PronunciationGenerator | 영문 용어 → 한글 발음 후보 자동 생성 (MariaDB → 마리아디비, 마리아데이터베이스) | 런타임 보정. 용어 등록 시점에 1회 실행 | 오프라인 |
| Span Detector | 문장에서 "용어일 수 있는 구간"을 찾는다. 한글 음차 패턴, 영문 혼용 위치 | 교체 | 1~3ms |
| Dictionary Matcher | 등록된 변형과 정확히 일치하면 후보 생성 | 유사 매칭 | 1ms |
| Phonetic Matcher | 자모 분해 후 발음 거리로 상위 N개 후보 생성 | 문맥 판단 | 5ms 이하 |
| Context Scorer | 앞뒤 단어 공기(테이블, 조회, 커넥션), 최근 사용 용어로 점수 가산 | 후보 생성 | 5ms 이하 |
| Ranker | 점수 합산 → 임계값 이상만 교체, 애매하면 원문 유지 | — | 1ms |
| Final Corrector (LLM) | 발화 종료 후 문장 전체 정리, 필러 제거(Polished 모드) | 실시간 Partial 처리 | 300~800ms |

### 음소 보정 보완 사항

한국어 STT가 내는 것은 "마뤼아뒤비"이고 정답은 "MariaDB"다. 두 문자열은 문자 체계가 달라 자모 거리를 바로 잴 수 없다. 그래서 PronunciationGenerator가 미리 "마리아디비" 같은 한글 발음 표기를 만들어 두고, Phonetic Matcher는 STT 결과와 이 표기 사이의 거리를 잰다.

거리 계산은 자모 단위 편집 거리에 "헷갈리기 쉬운 음 쌍"의 비용을 낮춘 가중치를 쓴다. 예: ㅣ/ㅟ, ㅓ/ㅗ, ㄷ/ㄸ, 받침 탈락. 이 가중치 표는 수정 로그가 쌓이면 데이터로 다시 맞춘다.

### 오보정 방지 장치

오보정은 미인식보다 비싸다. 사용자는 "못 고친 것"은 참지만 "멀쩡한 말을 바꾼 것"은 신뢰를 잃는다.

- **임계값 2단계:** 높은 점수는 자동 교체, 중간 점수는 Partial 화면에 밑줄로 후보 표시, 낮은 점수는 원문 유지.
- **도메인 게이트:** 문장에 개발 문맥 신호가 하나도 없으면 음소 매칭 단독으로는 교체하지 않는다. "마리아 뒤 비가 오기 시작했어" 같은 경우가 여기서 걸러진다.
- **원문 보존:** 모든 교체는 raw 텍스트와 오디오 구간 타임스탬프를 같이 저장한다. 되돌리기와 개인화 데이터 양쪽에 쓴다.

### Final Corrector (LLM)

Final Corrector의 LLM은 STT 모델과 함께 엔진 프로세스 안에 내장한다(llama.cpp 등으로 GGUF 모델을 직접 로드). 엔진 시작 시 두 모델을 모두 RTX 5080(16GB)에 올려 상주시키고, LLM은 설정 파일의 모델 경로만 바꿔 교체할 수 있게 한다. 소형 모델(Gemma·Qwen 계열 4B 안팎)로 시작한다. 입력은 STT 원문, Fast 보정 결과, 용어 목록, 모드(Verbatim/Polished)다.

LLM 출력은 그대로 쓰지 않는다. 원문과의 차이가 일정 비율을 넘거나 등록 용어가 사라지면 Fast 결과로 되돌린다. LLM이 의미를 바꾸는 사고를 막는 안전장치다.

Final Corrector는 **Polished(단축키 B)에서만** 실행한다. Verbatim(단축키 A)은 Fast 보정과 규칙(문장부호)으로 끝내고 안전 검사로 간다. LLM ON/OFF의 정확도 차이는 1-4에서 한 번 비교해 기록하되, 기본값은 OFF다.

## Transcript 관리와 출력

Partial은 우리 앱이 그리는 오버레이에만 표시하고, 대상 앱의 커서에는 확정된 텍스트만 넣는다. 이것이 1단계 UX에서 가장 중요한 결정이다.

### TranscriptBuffer: 3구간 관리

원 기획의 Confirmed/Partial 2구간에 "Stable" 구간을 추가한다.

| 구간 | 정의 | 누가 확정하나 | 보정 |
|---|---|---|---|---|
| Confirmed | STT 엔진이 Final로 확정 + Fast 보정 완료 | STT 엔진 | 확정 |
| Stable | 아직 Partial이지만 최근 N번(예: 3번) 갱신 동안 바뀌지 않은 앞부분 | TranscriptBuffer | Fast 보정 실행 |
| Unstable | 계속 바뀌는 꼬리 부분 | — | 보정하지 않고 표시만 |

Stable 구간이 있어야 STT의 Final을 기다리지 않고 보정을 시작할 수 있다. 사용자는 말하는 도중에 "마뤼아뒤비"가 "MariaDB"로 바뀌는 걸 본다. 계속 바뀌는 꼬리까지 보정하면 화면이 깜빡이고 연산만 낭비한다.

### 출력: 1단계는 OS 커서 하나에 집중

출력 대상 5종 중 1단계에서 실제로 만드는 것은 "현재 OS 커서 위치" 하나다. 나머지는 OutputAdapter 인터페이스만 정의해 둔다.

| 방식 | 장점 | 단점 | 판정 |
|---|---|---|---|---|
| 클립보드 + 붙여넣기 단축키 | 거의 모든 앱에서 동작, 한글 IME 영향 없음 | 사용자 클립보드를 덮어씀 → 백업/복원 필요 | 1단계 기본값 |
| 키 입력 시뮬레이션 (SendInput 유니코드) | 클립보드 오염 없음 | 한글 IME 상태와 충돌, 긴 문장에서 느림 | 짧은 텍스트용 보조 |
| 접근성 API로 입력창 값 직접 수정 | 정확한 위치 제어 | 앱마다 지원이 다름 | 2단계 이후 검토 |

입력 시점은 발화 종료(버튼 OFF) 후 Final 보정이 끝난 뒤 한 번이다. Final이 늦어지면 Fast 결과를 먼저 넣고 Final로 교체하는 방식은 대상 앱의 실행 취소 기록을 꼬이게 하므로 쓰지 않는다. 대신 Final에 시간 상한(예: 800ms)을 두고 넘으면 Fast 결과를 넣는다.

입력은 발화 ID당 한 번이다. 버튼 OFF 기준 전체 deadline(Verbatim 700ms, Polished 1.2초)을 두고 만료된 작업의 결과는 폐기한다. 붙여넣기 전후에 클립보드 시퀀스 번호를 확인해 그 사이에 사용자가 복사한 내용을 덮어쓰지 않고, 포커스가 바뀌면 입력을 취소한다.

### 수정 로그 수집 (1단계부터)

원 기획의 개인화 데이터(24절)는 1단계에서 이미 수집을 시작한다. 저장 항목은 오디오 구간, STT 원문, Fast 결과, Final 결과, 사용자가 실제로 남긴 최종 텍스트다. 사용자가 입력 직후 커서 위치에서 고친 내용을 감지하는 것은 어렵기 때문에, 오버레이에 "직전 입력 수정" 단축키를 두고 그 수정만 정답으로 기록한다.

로그는 설정의 디스크 상한(기본 2GB)을 넘으면 오래된 오디오부터 지운다. 기록은 출력 경로 밖(별도 스레드)에서 한다.

## 성능 목표, 지연 예산, 평가 체계

성공 기준을 숫자 6개로 고정한다. 모든 Phase의 완료 판정은 이 숫자로 한다.

### KPI

| 지표 | 정의 | MVP 목표 | 측정 주체 |
|---|---|---|---|---|
| 첫 글자 지연 | 발화 시작 → 오버레이에 첫 Partial 표시 | p50 300ms, p95 600ms | Latency Tracer |
| 발화 종료 → 커서 입력 | 버튼 OFF → 대상 앱에 텍스트 삽입 완료 | p50 700ms, p95 1.2초 | Latency Tracer |
| CER | 문자 오류율 (일반 한국어 문장) | 엔진 기준선 대비 악화 없음 | 평가 스크립트 |
| 용어 재현율 | 정답에 있는 등록 용어 중 맞게 나온 비율 | 95% 이상 | 평가 스크립트 |
| 오보정률 | 용어가 아닌 말을 용어로 바꾼 비율 | 함정 세트 0건 (비율은 1-5 실사용 로그에서, 분모 = 비용어 구간 수) | 평가 스크립트 |
| 수정 없이 쓴 비율 | 입력 후 사용자가 고치지 않은 발화 비율 | 80% 이상 | 수정 로그 |

원 기획의 "체감 1초 이내 / 100~500ms"는 첫 글자 지연 기준으로 해석했다. 엔진 하나만으로 100ms는 현실적으로 어렵다. 300ms를 목표로 잡는다.

### 지연 예산 (발화 종료 → 커서 입력, 목표 700ms)

| 구간 | 담당 주체 | 예산 |
|---|---|---|---|
| 1차 STT 마지막 청크 + flush | 스트리밍 STT | 청크 크기(160ms) + 디코딩 ≈ 200~300ms |
| 2차 전체 재인식 (녹음 종료 즉시 병렬 시작) | 오프라인 STT | 10초 발화 기준 300ms 이내 목표, 1-0에서 실측 |
| Fast 보정 (남은 구간) | CorrectionEngine | 20ms |
| Final 보정 (Polished만) | 로컬 LLM | 300ms (상한 800ms). Verbatim은 0 |
| 클립보드 교체 + 붙여넣기 | OutputAdapter | 50ms |
| 전체 deadline | Core | 버튼 OFF 기준 Verbatim 700ms, Polished 1.2초. 만료 결과 폐기 |

### 테스트셋

평가는 사용자 본인 목소리 데이터로 한다. 공개 데이터셋은 개발용어 혼용 발화가 거의 없어 이 프로젝트의 핵심을 측정하지 못한다.

- **초기 세트 (1-0에 구축):** 개발 문맥 문장 150개 + 일반 문장 50개 + 함정 문장 30개, 총 230개. 사용자가 직접 읽어 녹음하고 정답 텍스트를 붙인다.
- **홀드아웃 분리:** 230문장을 사전·임계값 조정용 150과 홀드아웃 80으로 나눈다. 홀드아웃은 조정에 쓰지 않고 게이트 판정에만 쓴다.
- **함정 세트 30문장은 오보정 0건, 일반 50문장은 용어 오삽입 0건**이 1-3 게이트다. "오보정률 1%"는 분모(비용어 구간 수)를 정의하고 1-5 실사용 로그로 측정한다.
- **회귀 테스트:** 사전·가중치·모델을 바꿀 때마다 전체 세트를 다시 돌려 6개 지표를 비교한다. 오디오를 저장해 두므로 엔진을 바꿔도 같은 입력으로 비교한다.
- **측정 조건 기록:** 모델·리비전·런타임·정밀도·스레드·청크·언어·사전 크기·워밍업 여부. 지연은 batch 1, 발화 1/3/10/30초, p50/p95.

## 1단계 개정 로드맵

원 기획의 Phase 1-1~1-5 앞에 "1-0 평가 기반"을 추가하고, 각 단계에 숫자로 된 통과 기준을 붙였다. 기준을 못 넘으면 다음 단계로 가지 않고 그 단계에서 고친다.

[로드맵 다이어그램 — "6개 게이트를 숫자로 통과해야 다음 단계로 간다" (2026-10-08 라벨 갱신)]

| 단계 | 주요 개발 | 통과 기준(게이트) |
|---|---|---|
| 1-0 평가 기반 (강조) | 테스트셋 230문장 녹음 · 지연 계측기 · 평가 스크립트 | 구성 A0·B·C 기준표 완성 |
| 1-1 스트리밍 입력 | AudioCapture · STT Adapter · TranscriptBuffer · 오버레이 | 첫 글자 p50 300ms (160ms 청크) |
| 1-2 용어 사전 + 바이어싱 | VocabularyManager · 발음 표기 생성 · 엔진 부스팅 연동 | 커서 경로 용어 재현율 85% |
| 1-3 Fast 보정 | Span Detector · Phonetic · Context · Ranker · Stable 구간 | 용어 재현율 95% · 함정 세트 오보정 0건 |
| 1-4 Final 보정 | 로컬 LLM · Polished 전용 (Verbatim은 1-3에서 완성) | Polished 종료 → 입력 p50 700ms |
| 1-5 제품화 | 전역 단축키 · 클립보드 입력 · 수정 로그 · 2주 실사용 | 수정 없이 쓴 비율 80% |

원 기획의 "1-3 전문용어 + 발음 보정"을 둘로 나눴다. 1-2에서 엔진 바이어싱만으로 얼마나 올라가는지 먼저 재고, 1-3에서 사후 보정이 남은 차이를 메운다. 그래야 각 부품의 기여도를 따로 알 수 있다. 85%·95%·80% 등 게이트 수치는 1-0에서 측정한 기준선을 보고 다시 조정한다.

**게이트 정의 (2026-10-08 개정):** 1-0은 구성 A0(Nemotron 단일 + 종료 flush)·B(Nemotron + Qwen3-ASR)·C(Nemotron + Cohere)의 기준표 완성. 1-1 첫 글자 p50 300ms는 160ms 청크 기준. 1-2 용어 재현율은 커서 입력 경로 기준. 1-3 오보정은 함정 30문장 0건·일반 50문장 오삽입 0건. 1-4는 Polished 전용(등록 용어 보존 100%, 숫자·부정어 변경 0건, 종료→입력 p50 700ms). Verbatim 경로는 1-3에서 완성된다.

## 개발 착수 패키지

개발은 Claude Opus 5.5에게 맡긴다. 코드로 만들 수 있는 것은 전부 Opus가, 코드로 만들 수 없는 것은 사용자가 준비한다.

### Opus에게 맡길 범위

프로그램은 하나(Python)지만, 안에서 세 덩어리로 나눠 만든다.

| 덩어리 | 포함 단계 | 내용 |
|---|---|---|---|
| Core (엔진) | 3~7, 10~14, 16번 | 소리 수집·전처리, STT 모델 호출(1차·2차), 임시 텍스트 관리, 빠른 보정, LLM 호출, 안전 검사, 커서 입력, 수정 로그 |
| Shell (껍데기) | 1, 8, 9번 | 트레이 상주, 전역 단축키 A·B 감지, 오버레이 화면. Core에 시작·중지만 보내고 결과를 받아 그리기만 함 |
| 평가 도구 | 1-0 단계 | 테스트셋 녹음 도구, 채점 스크립트(CER·용어 재현율·오보정률), 지연 시간·VRAM 측정기 |

### 개발 원칙

- Core는 Shell 없이 단독 실행·테스트할 수 있어야 한다. 녹음 파일을 넣으면 텍스트가 나오는 형태.
- STT는 sherpa-onnx 단일 런타임을 기본으로 한다. transformers·vLLM·OpenVINO는 비교용 별도 가상환경.
- STT와 LLM은 각각 어댑터로 분리하고, 모델 선택은 설정 파일에서 어댑터 종류·모델·provider를 함께 바꾼다.
- 엔진 시작 시 모델을 적재해 상주시키고, 외부 서버 프로그램에 의존하지 않는다.
- Verbatim 경로는 LLM을 쓰지 않는다. LLM은 Polished 전용.
- 발화 전체 버퍼(PTT 상한 60초)와 2단계용 30초 링버퍼를 구분한다.
- 로드맵 순서(1-0 → 1-5)대로 진행하고, 각 단계 게이트를 통과해야 다음 단계로 간다.
- 모든 단계의 처리 시간을 기록해 지연 예산과 비교한다. 발화 ID당 입력은 한 번, 전체 deadline 만료 시 결과 폐기.
- 클라우드 API는 쓰지 않는다.

### 1-0 첫 작업 지시서

Opus에게 이 문서와 함께 아래 지시를 넘긴다.

1. 프로젝트 골격을 만든다. Core, Shell, 평가 도구, 모델 어댑터, 설정을 폴더로 분리한다. Python 3.12, sherpa-onnx는 PR #3895 포함 커밋을 고정한다.
2. 테스트 문장 230개 초안을 작성한다. 개발 문맥 150개, 일반 50개, 함정 30개. 일부는 "빠르게 말하기"로 표시하고, 사전 조정용 150 / 홀드아웃 80으로 나눈다.
3. 녹음 도구를 만든다. 문장을 한 줄씩 보여 주고 녹음해 16kHz 단일 채널 wav와 정답 텍스트를 저장한다.
4. STT 어댑터를 같은 인터페이스로 만든다. 스트리밍: sherpa-onnx Nemotron 3.5(160ms·560ms)와 대조군 zipformer-ko. 2차: Qwen3-ASR-1.7B(sherpa-onnx ONNX, transformers 대조)와 Cohere Transcribe. transformers 계열은 별도 venv.
5. 구성 A0(Nemotron 단일 + 종료 flush), A1(A0 + 동일 엔진 재인식), B(Nemotron + Qwen3-ASR, context OFF/ON), C(Nemotron + Cohere)를 같은 테스트셋으로 측정한다. 후보는 하나씩 적재, batch 1.
6. 채점 스크립트를 만든다. CER, 용어 재현율, 오보정·오삽입, 처리 시간(p50/p95)을 표로 출력한다.
7. 메모리를 측정한다. 각 모델 단독, 2차 STT + LLM 동시 적재 peak. GPU 측정은 집 PC.

**완료 기준:** 구성 A0·B·C의 지표표(CER, 용어 재현율, 오보정·오삽입, 10초 발화 재인식 지연 p50)와 메모리 측정표가 나온다. 이 결과로 1차·2차 STT와 런타임을 확정한다.

## 2단계 방향성 검토

2단계의 방향(VAD → 발화 분할 → Context Router → 우선순위 처리)은 맞다. 상세 설계는 1단계 구현 후 다시 검토하므로, 여기서는 방향 수정 3가지와 1단계에서 미리 심어둘 것만 정리한다.

### 유지할 방향

- Context Routing이 2단계의 핵심이라는 판단.
- Level 0~4 계층 처리(VAD → 규칙 → 경량 분류 → 소형 LLM → 대형 LLM). 모든 발화를 LLM에 보내지 않는 원칙.
- 고우선순위 발화는 LLM을 기다리지 않는다는 원칙.

### 바꿀 방향

바꿀 방향 세 가지(P0는 키워드 스포팅 경로, 긴급 감지의 실행 주체 정의, Speaker Resolver를 Router 앞단에)는 2단계 설계 때 다시 검토한다. 메모는 @file/e933317f-2774 탭에 있다.

### 1단계에서 미리 심어둘 것

- **오디오 링버퍼:** 캡처한 오디오를 최근 30초 정도 메모리에 계속 보관. 2단계에서 VAD가 늦게 감지해도 앞부분을 잃지 않는다.
- **이벤트 기반 Core 인터페이스:** Core는 "텍스트를 반환"하지 않고 PartialUpdated, SegmentStable, UtteranceFinalized 이벤트를 발행한다. 2단계 Router는 이 이벤트를 구독만 하면 된다.
- **발화 단위 메타데이터:** 모든 발화에 시작/종료 시각, 오디오 구간, 신뢰도, 입력 모드를 붙인다. Utterance Segmentation과 Context Stack이 이 데이터를 그대로 쓴다.
- **Controller 추상화 테스트:** 1단계 중에 "VAD로 시작/종료하는 PTT"를 실험 모드로 만들어 본다. Core가 버튼 없이도 동작하는지 미리 검증된다.
